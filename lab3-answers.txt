In this lab, we implemented transaction support in SimpleDB using locking to control concurrent access to pages. The goal was to make transactions follow atomicity, isolation, and durability. We used strict two-phase locking together with a NO STEAL / FORCE buffer policy. The main components we built were a lock manager, lock handling inside the buffer pool, deadlock detection, and correct commit and abort behavior.

We chose page-level locking because it strikes a reasonable balance between simplicity and concurrency. Locking at the tuple level would allow more parallelism, but it would also make the system significantly more complex to implement and reason about. With page-level locking, multiple transactions can still run at the same time as long as they access different pages.

The lock manager supports two lock types: shared locks for reading and exclusive locks for writing. Multiple transactions can hold a shared lock on the same page simultaneously, but only one transaction can hold an exclusive lock. If a transaction already holds the only shared lock on a page and no other transaction holds that page, it is allowed to upgrade to an exclusive lock. Internally, the lock manager uses a pageLocks map that tracks the current lock state and set of holders for each page, and a txnToPages map that tracks which pages each transaction holds. It also maintains a waits_For graph used for deadlock detection.

Locks are requested inside the getPage method of the buffer pool. When a transaction requests a page with READ_ONLY permission, it asks for a shared lock. When it requests READ_WRITE permission, it asks for an exclusive lock. If the lock cannot be granted immediately, the transaction enters a loop where it updates the wait-for graph with the current holders of the lock, checks for a deadlock cycle, and then waits before retrying. All of this logic is synchronized on the lock manager to avoid race conditions.

We implemented strict two-phase locking, meaning transactions never release locks early. Locks are held until the transaction commits or aborts, at which point releaseAllLocks releases everything at once. This guarantees isolation and prevents other transactions from reading uncommitted changes.

For buffer management, we used a NO STEAL and FORCE policy. In evictPage, the buffer pool scans for a clean page to evict. If all pages are dirty, it throws a DbException rather than evicting uncommitted data. This is the NO STEAL policy in practice. The FORCE policy is enforced in transactionComplete: when a transaction commits, flushPages writes all of that transaction's dirty pages to disk before releasing locks. When a transaction aborts, those same dirty pages are removed from the buffer pool with discardPage, restoring the old on-disk version. Because dirty pages are never written to disk before a commit, aborting is straightforward and safe.

For deadlock detection, we explored two different strategies and compared them directly, which we are submitting as our attempt at the bonus exercise.

Our first approach used a pure timeout policy. If a transaction waited longer than five seconds without acquiring a lock, it was aborted. This was simple to implement and always passed the tests, but the performance was poor. Each deadlock took the full five seconds to resolve, causing each test case to run in roughly 5.2 seconds. More importantly, the timeout would occasionally abort transactions that were not actually in a deadlock, they simply had to wait a long time due to contention. This is unnecessary work and hurts throughput.

Our second approach replaced the timeout with cycle detection over a wait-for graph. Whenever a transaction cannot acquire a lock, it records edges to all current lock holders in waits_For and then calls detectDeadLock, which runs a depth-first search starting from the current transaction. The DFS carefully distinguishes between back edges that form a cycle involving the current transaction versus cycles among unrelated transactions, so it only aborts when a real deadlock exists. With this approach, each test case resolved in around 0.22 seconds, more than twenty times faster. Crucially, it also only aborts transactions when a deadlock is genuinely detected, avoiding unnecessary aborts under contention.

We finally went with cycle detection as our final implementation. The timeout policy was too conservative and slow, while the wait-for graph gives precise, fast deadlock resolution. We kept the 5-second timeout as a fallback safety net in case an edge case escapes the cycle detector, but in practice the cycle detection fires first in every scenario we tested.

We did not make any changes to the provided API. All existing method signatures in BufferPool and related classes were preserved.

A good addition would be a test for holdsLock(). assert it returns true after a transaction acquires a page, false for a different transaction that never held the lock, and false again after calling releasePage().

In general, this lab gave us a clear understanding of how database systems manage concurrency and recovery. The trickiest parts were correctly maintaining the wait-for graph as lock states changed, handling lock upgrades without introducing subtle races, and ensuring the eviction policy never let dirty pages escape to disk. Comparing the two deadlock strategies made clear that precise cycle detection is strongly preferable to timeout-based approaches for both performance and correctness.
